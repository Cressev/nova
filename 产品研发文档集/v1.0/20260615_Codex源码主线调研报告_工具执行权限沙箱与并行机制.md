# Codex 源码主线调研报告：工具执行、权限、沙箱、取消与并行机制

> 本报告以 [Codex 源码 references/upstream/openai-codex](../../references/upstream/openai-codex) 为主线。CC、Crush、Hermes、OpenClaw 只作为最后的对照材料，不抢主线。
>
> 阅读目标不是“把源码罗列一遍”，而是回答 Nova 现在最核心的问题：一个用户在对话里说“帮我执行/修改/安装/搜索/停止”，Codex 是怎样从模型工具调用一路走到真实系统命令，又怎样把风险、输出、取消、并行和 UI 状态串起来的。

## 0. 先建立一条主线：Codex 真正保护的不是 bash，而是“工具调用落地链路”

如果只看表面，Codex 也有一个 `shell_command` 工具，似乎和 Nova 现在的 shell 工具差不多：模型给一个命令，宿主执行命令，再把 stdout/stderr 返回给模型。

但源码读下来，Codex 的重点并不在“shell 工具函数怎么写”。它真正做的是把一次工具调用拆成几个清楚的阶段：

1. 模型输出工具调用。
2. `ToolRouter` 把模型输出转成内部 `ToolCall`。
3. `ToolCallRuntime` 决定这个工具能不能和其他工具并行、取消时是否要等待工具自己清理。
4. `ShellCommandHandler` 把用户可读的命令参数转成 `ExecParams`。
5. `ExecPolicy` 先判断命令是否需要审批、是否禁止、是否可放行。
6. `ToolOrchestrator` 统一处理审批、hook、沙箱选择、第一次执行、沙箱失败后的二次审批和重试。
7. `ShellRuntime` 根据当前沙箱尝试构造真正要 spawn 的命令。
8. `exec.rs` 才负责真正启动进程、读 stdout/stderr、截断输出、识别超时/取消/沙箱拒绝。

这条链路的重要结论是：Codex 没有把安全逻辑硬塞进 bash 函数，也没有靠一个简单黑名单决定一切。它把“策略判断”“审批交互”“沙箱执行”“进程生命周期”“工具 UI 事件”拆成了不同模块。

Nova 要对标 Codex，第一步不是再加几个 if，而是把当前 shell 工具拆成类似的执行链路。

- [模型输出转内部 ToolCall references/upstream/openai-codex/codex-rs/core/src/tools/router.rs ToolRouter.build_tool_call #L96-L130](../../references/upstream/openai-codex/codex-rs/core/src/tools/router.rs#L96-L130)

源码摘录：

```rust
// Codex 内部统一的工具调用对象：后续审批、并行、取消、日志都围绕它走。
pub struct ToolCall {
    // 工具名，例如 shell_command、apply_patch、tool_search。
    pub tool_name: ToolName,
    // 本次工具调用的唯一 id，用来关联模型输出、工具事件、审批结果和最终返回。
    pub call_id: String,
    // 工具参数载荷。shell 是 Function arguments，tool_search/MCP 会有不同 payload。
    pub payload: ToolPayload,
}

pub fn tool_supports_parallel(&self, call: &ToolCall) -> bool {
    // 并行能力不是模型声明的，而是从宿主注册表读取。
    self.registry
        .supports_parallel_tool_calls(&call.tool_name)
        // 找不到工具时默认不并行，这是 fail-closed 的做法。
        .unwrap_or(false)
}
```

这段代码说明，Codex 先把模型输出变成自己的 `ToolCall`，后面所有运行时逻辑都围绕这个内部对象走。并行能力也不是模型自己说了算，而是查工具注册表。

`ToolRouter` 做的第一件事，是把模型返回的 `ResponseItem::FunctionCall` 变成内部 `ToolCall`。这个内部结构包含三个核心字段：

- `tool_name`：工具名，比如 `shell_command`。
- `call_id`：这一次工具调用的唯一 id。
- `payload`：工具参数。shell 工具就是 function arguments。

这一步看起来普通，但它解决了一个关键问题：模型输出格式和宿主运行时不能直接耦合。模型可以输出 function call、tool search call、MCP call；宿主统一转成 `ToolCall`，后面的并行、审批、hooks、日志都只看这个内部对象。

源码里 `ToolRouter::build_tool_call()` 在 `router.rs:96-130` 做这件事。它不是立刻执行，而是只构造工具调用对象。真正执行要交给 `ToolCallRuntime`。

对 Nova 的启发：

Nova 现在已经切到 OpenAI-compatible `tool_calls`，这是对的。但下一步要避免 provider 层、agent 层、shell 层互相穿透。应该有一个稳定的内部结构，例如：

```python
@dataclass
class ToolCall:
    # Nova 内部工具名，不直接暴露 provider 的原始格式。
    tool_name: str
    # 单次调用 id，用于工具卡片、Langfuse trace、审批回填。
    call_id: str
    # 已经解析成 dict 的工具参数。
    arguments: dict
    # 调用来源，区分模型、slash 指令、系统重试等不同入口。
    source: Literal["model", "slash", "system", "retry"]
    # 给前端工具卡片用的短说明，不能传进真实工具参数。
    annotation: str | None = None
```

其中 `annotation` 是 Nova 前端显示工具卡片标题需要的“这条工具调用的目的”。它只能作为 UI/trace 元数据，不能混进工具真实参数。

- [shell 声明支持并行 references/upstream/openai-codex/codex-rs/core/src/tools/handlers/shell/shell_command.rs supports_parallel_tool_calls #L140-L142](../../references/upstream/openai-codex/codex-rs/core/src/tools/handlers/shell/shell_command.rs#L140-L142)

源码摘录：

```rust
// 先查工具是否允许并行；这是工具注册表的静态能力，不是模型说了算。
let supports_parallel = self.router.tool_supports_parallel(&call);
// 有些工具被取消时需要自己清理资源，shell 就属于这一类。
let wait_for_runtime_cancellation =
    self.router.tool_waits_for_runtime_cancellation(&call);

let mut handle: AbortOnDropHandle<Result<AnyToolResult, FunctionCallError>> =
    AbortOnDropHandle::new(tokio::spawn(async move {
        // 支持并行的工具拿读锁：多个读锁可以同时存在。
        let _guard = if supports_parallel {
            Either::Left(lock.read().await)
        } else {
            // 不支持并行的工具拿写锁：写锁独占，其他工具必须等它完成。
            Either::Right(lock.write().await)
        };

        // 真正执行工具调用。锁 guard 活着期间，这个工具占用对应并行槽位。
        router
            .dispatch_tool_call_with_terminal_outcome(
                session,
                turn,
                invocation_cancellation_token,
                tracker,
                dispatch_call,
                source,
                dispatch_terminal_outcome_reached,
            )
            .instrument(dispatch_span.clone())
            .await
    }));
```

这里的 `_guard` 就是并行控制的核心。支持并行的工具拿读锁，可以同时跑；不支持并行的工具拿写锁，会独占执行窗口。

`ToolCallRuntime` 里有一个很关键的字段：

```rust
// 所有工具调用共享这把读写锁，用它在宿主侧兜底并行/串行语义。
parallel_execution: Arc<RwLock<()>>
```

这里的 `RwLock` 可以理解成“读写锁”：多个读锁可以同时存在，一个写锁会独占。Codex 用它表达工具并行能力：

- 工具声明支持并行：拿读锁，可以和其他支持并行的工具一起跑。
- 工具不支持并行：拿写锁，会阻塞其他工具，保证串行。

具体逻辑在 `parallel.rs:113-119`：

- `supports_parallel == true` 时，`lock.read().await`。
- 否则 `lock.write().await`。

这说明 Codex 的并行机制不是“模型一次返回多个 tool_calls 就并行”。模型只是给出多个调用，宿主还要判断每个工具是否适合并行。

shell 工具在 `shell_command.rs:140-142` 返回 `true`，表示它允许并行。这个选择很激进，因为两个 shell 命令可能同时写文件。但 Codex 后面依靠沙箱、审批和具体命令策略兜底。其他工具可以选择不支持并行，例如某些写文件、修改状态、安装插件类工具就应该串行。

对 Nova 的启发：

Nova 不能把“并行”完全交给模型，也不能只做 `asyncio.gather(tool_calls)`。它需要每个工具有元数据：

```python
@dataclass
class ToolSpec:
    # 工具名。
    name: str
    # 是否允许和其他工具同时执行。
    supports_parallel: bool
    # 取消时是否等待工具自己完成清理，例如 shell 需要杀进程树。
    waits_for_runtime_cancellation: bool
    # 只读工具通常可以更大胆地并行。
    read_only: bool
    # 破坏性工具默认应该串行，并进入审批链路。
    destructive: bool
```

执行器按工具元数据决定：

- 多个 `read_file`、`grep`、`ls` 可以并行。
- `apply_patch`、`write_file`、`git commit`、`npm install` 默认串行。
- shell 命令可以先按 Codex 设为并行，但要配合审批和 cwd/工作树隔离。

如果 Nova 后续要更稳，可以比 Codex 更细一点：shell 工具先用命令分类判断读写，读命令并行，写命令串行。

## 3. Codex 的停止按钮为什么能生效：取消信号贯穿到工具运行时

源码位置：

- [取消 select 分支 references/upstream/openai-codex/codex-rs/core/src/tools/parallel.rs handle_tool_call_with_source #L136-L175](../../references/upstream/openai-codex/codex-rs/core/src/tools/parallel.rs#L136-L175)
- [合成取消结果 references/upstream/openai-codex/codex-rs/core/src/tools/parallel.rs aborted_response #L213-L235](../../references/upstream/openai-codex/codex-rs/core/src/tools/parallel.rs#L213-L235)
- [shell 等待运行时清理 references/upstream/openai-codex/codex-rs/core/src/tools/handlers/shell/shell_command.rs waits_for_runtime_cancellation #L210-L212](../../references/upstream/openai-codex/codex-rs/core/src/tools/handlers/shell/shell_command.rs#L210-L212)
- [shell 合并 timeout 与 cancellation references/upstream/openai-codex/codex-rs/core/src/tools/runtimes/shell.rs ShellRuntime.run #L300-L306](../../references/upstream/openai-codex/codex-rs/core/src/tools/runtimes/shell.rs#L300-L306)

源码摘录：

```rust
tokio::select! {
    // 第一条分支：工具正常执行完成。
    res = &mut handle => res.map_err(Self::tool_task_join_error)?,
    // 第二条分支：用户或上层 turn 发出取消信号。
    _ = cancellation_token.cancelled() => {
        if wait_for_runtime_cancellation {
            // The abort owns the terminal outcome; await only so
            // the runtime can finish process teardown.
            // 中文解释：shell 这类工具要先完成进程清理，再返回取消结果。
            match handle.await {
                Ok(_) => {}
                Err(err) if err.is_cancelled() => {}
                Err(err) => return Err(Self::tool_task_join_error(err)),
            }
        } else {
            // 普通工具不需要清理时，直接 abort 宿主任务。
            handle.abort();
        }
        // 合成一个模型可见、UI 可见的 aborted 工具结果。
        let response = Self::aborted_response(&call, secs);
        Ok(response)
    },
}
```

```rust
fn waits_for_runtime_cancellation(&self) -> bool {
    // shell 命令取消时必须等待 runtime 清理，否则进程可能继续留在后台。
    true
}
```

shell 工具返回 `true`，所以用户点停止后，Codex 会等 shell runtime 完成进程清理，再给模型和 UI 返回取消结果。

Codex 的取消不是前端把流断掉就结束。它有一个 `CancellationToken`，从 turn 级别传入每个工具调用。

在 `parallel.rs:136-175`，运行时用 `tokio::select!` 同时等待两件事：

- 工具正常返回。
- `cancellation_token.cancelled()` 触发。

取消后有两种处理方式：

1. 如果工具声明 `waits_for_runtime_cancellation()` 为 true，就等待工具自己做完清理。
2. 否则直接 abort 任务，并合成一个 “aborted by user” 的工具结果。

shell 工具在 `shell_command.rs:210-212` 明确返回 true，也就是 shell 取消时，Codex 不会粗暴丢弃任务，而是等 shell runtime 把进程清理干净。

到 `ShellRuntime` 里，`runtimes/shell.rs:302-305` 把请求 timeout 和 cancellation token 合并成 `ExecExpiration`。这意味着真正的进程执行层也能感知用户取消。

对 Nova 的启发：

Nova 的停止按钮必须满足三个层次：

1. 前端立即停止当前 SSE 渲染，让用户看到按钮有反馈。
2. 后端 session 立即标记 cancel requested，让 agent loop 不再继续下一轮模型调用。
3. 正在运行的工具收到 cancel token，shell 进程树被终止，工具卡片进入 `cancelled` 或 `aborted` 终态。

只做到第一层就是“看似停止，实际后台还在跑”；只做到第二层会出现“当前命令停不下来”；只做到第三层但前端状态不同步，就会出现用户看到按钮不能点或工具卡一直 running。

Nova 后续应把运行态建模为：

```python
class TurnRun:
    # 当前 turn 的唯一 id。
    id: str
    # 整轮对话共享取消信号，停止按钮会触发它。
    cancellation: CancellationToken
    # 正在运行的工具任务，用于取消、UI 状态、后台任务管理。
    active_tool_calls: dict[str, ToolTask]
    # 用户在运行中继续发送的消息，当前工具轮结束后再进入上下文。
    queued_user_messages: list[str]
```

停止按钮调用 `/cancel` 后：

- `TurnRun.cancellation.cancel()`
- 遍历 `active_tool_calls`，调用工具自己的 `cancel()`
- agent loop 检查 token 后退出
- 前端收到 `turn.cancelled` 和每个 `tool.cancelled`

这段源码直接证明：`shell_command` 自己不决定“能不能执行”。它先生成审批要求和 `ShellRequest`，然后交给 orchestrator。

`ShellCommandHandler` 负责把模型参数转成 `ExecParams`：

- `command`：由用户 shell 派生出的 argv，不是简单字符串拼接。
- `cwd`：根据 turn 当前工作目录解析。
- `timeout`：来自工具参数。
- `env`：由 shell 环境策略创建。
- `network`：当前 turn 的网络代理策略。
- `sandbox_permissions`：工具是否请求额外权限。

真正关键的是 `handlers/shell.rs:163-181`。这里会调用 `exec_policy.create_exec_approval_requirement_for_command()`，生成 `ExecApprovalRequirement`。这个对象代表“这条命令要不要审批、能不能直接运行、是否禁止”。

然后 `handlers/shell.rs:183-200` 构造 `ShellRequest`，把命令、cwd、timeout、cancel token、网络、沙箱权限、审批结论都塞进去。

最后 `handlers/shell.rs:201-217` 创建 `ToolOrchestrator` 和 `ShellRuntime`，由 orchestrator 来跑：

```rust
orchestrator.run(&mut runtime, &req, &tool_ctx, &turn, approval_policy)
```

这就是 Codex 的核心分层：handler 只做参数适配和事件开始/结束，真正的安全决策交给策略和 orchestrator。

对 Nova 的启发：

Nova 现在最大的问题之一，是 shell 工具里混合了：

- 参数解析
- 命令安全判断
- 审批
- 执行
- stdout/stderr
- 前端事件
- 后台任务
- 取消

这会导致每次改一个功能都牵动整个链路，也容易出现“为了用户一句话硬编码一个 netsh 命令”这种错误。

Nova 应拆成：

- `tools/shell_command.py`：只定义 schema、参数解析、命令转 `ExecRequest`。
- `security/exec_policy.py`：只负责决策。
- `runtime/tool_orchestrator.py`：只负责审批、沙箱、重试、hooks。
- `processes/exec.py`：只负责进程生命周期。
- `events/tool_events.py`：只负责前端可观察事件。

Codex 不是“未知命令一律拒绝”。它会结合危险度、沙箱是否真实存在、用户审批策略一起判断。

Codex 的 `exec_policy` 不是简单“允许 pwd/ls/cat，禁止 rm/sudo”。它有规则文件、配置层、启发式判断和审批策略组合。

先看 `exec_policy.rs:52-99` 的 `BANNED_PREFIX_SUGGESTIONS`。这里列了很多不能被建议成“以后都允许这个前缀”的命令前缀，比如：

- `python -c`
- `node -e`
- `bash -lc`
- `sh -c`
- `powershell -Command`
- `sudo`
- `env`

注意，这不是说这些命令永远不能运行，而是说不能把它们轻易加入“允许前缀”。原因很直接：这些前缀太宽，真正危险的内容藏在字符串参数里。如果用户 approve 了 `bash -lc`，那后面任何 shell 字符串都可能借这个前缀绕过审批。

再看 `render_decision_for_unmatched_command()`，源码在 `exec_policy.rs:631-750`。它处理“没有命中显式规则的命令”。核心逻辑是：

1. 如果命令是已知安全命令，并且解析不复杂，在某些策略下直接允许。
2. 如果命令可能危险，或者当前环境没有真实沙箱保护，则进入审批或禁止。
3. 如果命令不危险，在 `Never` / `OnFailure` 下允许，但依赖沙箱兜底。
4. 在 `OnRequest` 下，如果是 restricted sandbox，非危险且未请求逃逸沙箱的命令可以直接运行。
5. 如果命令请求沙箱 override，就提示用户审批。

这套逻辑比“黑名单 + 白名单”更重要。它不是把所有未知命令拒掉，而是问：

- 当前有没有沙箱？
- 用户当前 approval policy 是什么？
- 命令是不是已知安全？
- 命令是不是危险？
- 命令有没有请求逃逸沙箱？
- 是否允许给用户弹审批？

对 Nova 的启发：

第二步，选择第一次沙箱。

第三步，执行第一次尝试。

- 当前策略是否允许无沙箱运行。
- 是否存在 network approval context。
- 是否已经审批过。
- strict auto-review 是否要求重新审查。

```python
async def run_tool(call, runtime, turn):
    # 先由策略引擎判断 allow/prompt/forbid。
    requirement = exec_policy.decide(call, turn.policy)

    if requirement == FORBID:
        # forbidden 不进入审批，也不进入执行。
        return rejected_result()

    if requirement == PROMPT:
        # pending approval：前端应该展示 approve/deny。
        decision = await approval_service.request(call)
        if not decision.approved:
            return rejected_result()

    # 第一次尝试通常在当前沙箱中运行。
    first_attempt = sandbox_manager.select_attempt(call, turn)
    result = await runtime.run(call, first_attempt)

    if result.sandbox_denied and runtime.escalate_on_failure:
        # 只有明确识别为 sandbox denied，才进入重试审批。
        decision = await approval_service.request_retry(call, reason=result.reason)
        if decision.approved:
            # 用户批准后再构造 retry attempt。
            retry_attempt = sandbox_manager.select_retry_attempt(call, turn, decision)
            return await runtime.run(call, retry_attempt)

    return result

pub(crate) fn sandbox_override_for_first_attempt(
    sandbox_permissions: SandboxPermissions,
    exec_approval_requirement: &ExecApprovalRequirement,
    file_system_sandbox_policy: &FileSystemSandboxPolicy,
) -> SandboxOverride {
    // Deny-read restrictions are part of the active permission policy. Running
    // without a filesystem sandbox would discard them, even if the command was
    // otherwise approved by rules or explicit escalation.
    // 中文解释：如果有“禁止读取”的路径，不能为了提权直接丢掉沙箱。
    if !unsandboxed_execution_allowed(file_system_sandbox_policy) {
        return SandboxOverride::NoOverride;
    }

    // exec policy 明确允许跳过沙箱时，第一次尝试就可以绕过。
    if matches!(exec_approval_requirement, ExecApprovalRequirement::Skip { bypass_sandbox: true, .. }) {
        return SandboxOverride::BypassSandboxFirstAttempt;
    }

    // 工具显式请求提升权限时，允许第一次尝试绕过默认沙箱。
    if sandbox_permissions.requires_escalated_permissions() {
        SandboxOverride::BypassSandboxFirstAttempt
    } else {
        SandboxOverride::NoOverride
    }
}
```

```rust
pub(crate) fn unsandboxed_execution_allowed(
    file_system_sandbox_policy: &FileSystemSandboxPolicy,
) -> bool {
    // 只有不存在 denied-read 限制时，无沙箱运行才不会扩大读取范围。
    !file_system_sandbox_policy.has_denied_read_restrictions()
}
```

用户批准“提升权限”并不等于可以丢掉所有限制。Codex 特意保留 denied reads，防止提权后反而泄露受保护文件。

这里有个容易被忽略的细节：如果当前文件系统策略里有 denied-read path，Codex 不允许直接 bypass sandbox。

原因写在 `sandboxing.rs:277-287`：某些“禁止读取”的限制只存在于沙箱里。如果你为了执行命令方便直接无沙箱运行，就等于把这些 denied-read 限制全丢了。

所以 `sandbox_override_for_first_attempt()` 会先调用 `unsandboxed_execution_allowed()`。如果 denied reads 存在，就返回 `NoOverride`。即使命令请求 escalated，也不能无脑脱离沙箱。

对 Nova 的启发：

Nova 现在如果只有 `read_only / workspace_write / danger_full_access` 三档，会不够表达“允许写项目，但禁止读某些密钥文件”。后续至少要支持：

- writable roots：可写目录。
- readable roots：可读目录。
- denied read paths：禁止读取的路径，比如 `.env`、密钥目录。
- denied write paths：禁止写的路径，比如 `.git` 里的危险文件。

当用户批准“提升权限”时，Nova 也不能直接跳到 `danger_full_access`。它应该像 Codex 一样保留 denied reads，除非用户明确批准对应路径。

pub(crate) fn is_likely_sandbox_denied(
    sandbox_type: SandboxType,
    exec_output: &ExecToolCallOutput,
) -> bool {
    // 没开沙箱或命令成功时，不判定为沙箱拒绝。
    if sandbox_type == SandboxType::None || exec_output.exit_code == 0 {
        return false;
    }

    // Codex 用输出关键字辅助判断沙箱拒绝，因为 exit code 本身不够可靠。
    const SANDBOX_DENIED_KEYWORDS: [&str; 7] = [
        "operation not permitted",
        "permission denied",
        "read-only file system",
        "seccomp",
        "sandbox",
        "landlock",
        "failed to write file",
    ];

    // 同时检查 stderr、stdout 和聚合输出。
    let has_sandbox_keyword = [
        &exec_output.stderr.text,
        &exec_output.stdout.text,
        &exec_output.aggregated_output.text,
    ]
    .into_iter()
    .any(|section| {
        let lower = section.to_lowercase();
        SANDBOX_DENIED_KEYWORDS
            .iter()
            .any(|needle| lower.contains(needle))
    });
}

`exec.rs` 不负责“审批”，它负责“可靠执行”：输出上限、分片、超时、取消、沙箱拒绝识别都在这一层。

`exec.rs` 是最低层进程执行模块。它关心的不是“这个命令该不该执行”，而是“已经决定执行了，怎样可靠地执行”。

几个值得 Nova 直接学习的点：

第一，输出必须有硬上限。

`exec.rs:64-72` 定义了 exec stdout/stderr/aggregated output 的最大保留字节数，以及 live delta 事件数量上限。原因很实际：一个命令可能打印无限输出，如果不截断，会拖垮 Agent 进程和浏览器。

第二，stdout/stderr drain 要有超时。

`exec.rs:74-81` 注释解释了一个真实问题：子进程被 kill 后，它的孙进程可能继承 stdout/stderr fd，导致读取任务永远挂住。所以 Codex 给 IO drain 设置 2 秒超时。

第三，`ExecExpiration` 同时表达 timeout 和 cancellation。

`exec.rs:151-170` 定义：

- `Timeout`
- `DefaultTimeout`
- `Cancellation`
- `TimeoutOrCancellation`

这比“timeout_ms 一个字段 + cancel 另一个 if”更干净。执行层只需要等待 expiration 完成，并知道结果是 timed out 还是 cancelled。

第四，`build_exec_request()` 只负责把抽象请求转换成具体 sandbox exec request。

`exec.rs:328-438` 根据 permission profile 选择 sandbox 类型，再调用 `SandboxManager.transform()` 生成真正可执行的请求。

第五，`exec()` 只执行，不再做沙箱判断。

`exec.rs:934-945` 的注释说得很明确：这个函数不应用任何沙箱逻辑，调用者负责提前构造已经包含 sandbox wrapper 的命令。

第六，沙箱拒绝不是只看 exit code。

`is_likely_sandbox_denied()` 在 `exec.rs:809-869` 同时检查：

- sandbox 是否启用。
- exit code 是否非 0。
- stdout/stderr/aggregated output 是否包含 `operation not permitted`、`permission denied`、`read-only file system`、`seccomp`、`sandbox`、`landlock` 等关键词。
- Linux seccomp 的特定信号。

async fn handle_exec_approval(
    codex: &Codex,
    turn_id: String,
    parent_session: &Arc<Session>,
    parent_ctx: &Arc<TurnContext>,
    event: ExecApprovalRequestEvent,
    cancel_token: &CancellationToken,
) {
    // 子 Agent 发来的审批事件要先解析出 approval id。
    let approval_id_for_op = event.effective_approval_id();
    let ExecApprovalRequestEvent {
        // 子 Agent 请求执行的工具调用 id。
        call_id,
        // 可选审批 id，用于回填结果。
        approval_id,
        // 子 Agent 想执行的命令和目录。
        command,
        cwd,
        // 请求审批时展示给用户/guardian 的理由。
        reason,
        // 网络、规则修订、额外权限都要透传给父会话审批。
        network_approval_context,
        proposed_execpolicy_amendment,
        additional_permissions,
        available_decisions,
        ..
    } = event;

    // 真正的审批发生在 parent_session，而不是子 Agent 自己决定。
    let decision = await_approval_with_cancel(
        parent_session.request_command_approval(
            parent_ctx,
            call_id,
            approval_id,
            command,
            cwd,
            reason,
            network_approval_context,
            proposed_execpolicy_amendment,
            additional_permissions,
            available_decisions,
        ),
        parent_session,
        &approval_id_for_op,
        cancel_token,
        None,
    )

            turn_id: Some(turn_id),

子 Agent 没有自己的独立审批世界。它的 shell、patch、权限请求都会回到父 session，由父会话统一决定。

Codex 的 delegated subagent 不是“子 Agent 想干什么就干什么”。当子 Agent 要执行命令、apply patch、请求权限时，父会话要接管审批。

`handle_exec_approval()` 在 `codex_delegate.rs:442-522` 做 shell 审批转发。它把子 Agent 的审批事件转成父 session 的审批请求，等父会话决定后，再把 decision submit 回子 Agent。

`await_approval_with_cancel()` 在 `codex_delegate.rs:840-866` 处理取消。如果父会话取消了等待，就通知 approval 为 `Abort`。

对 Nova 的启发：

Nova 后续做子 Agent 时，权限不能散。正确模型是：

- 子 Agent 可以有自己的上下文和任务。
- 子 Agent 的工具请求必须回到父 session 的 `ApprovalService`。
- 父 session UI 显示“子 Agent X 请求执行命令 Y”。
- 用户 approve/deny 后，结果回到子 Agent。
- 父 turn 取消时，子 Agent pending approval 一律 abort。

这能避免子 Agent 变成绕过主会话权限的后门。

hook 是工具协议的一部分，不是 shell 的特殊 if。Nova 也应该把 hook 接到 orchestrator 层，而不是塞进单个工具。

Codex 的 hooks 不是 shell 工具私有逻辑。`CoreToolRuntime` 有 `pre_tool_use_payload()` 和 `post_tool_use_payload()`，工具可以暴露稳定的 hook 输入输出。

shell 工具的 pre hook payload 是：

```json
{ "command": "..." }
```

这里的 `command` 就是即将执行的 shell 命令文本。hook 可以根据它做审计、阻断或改写，但最终仍要回到统一工具事件和审批链路。

post hook payload 包括 tool_use_id、tool_input、tool_response。

permission request hooks 在 orchestrator 的审批阶段执行，优先级高于普通用户审批。这意味着企业/本地策略可以直接拦截某些命令。

对 Nova 的启发：

Nova 的 hook 接口应该分三类：

- `pre_tool_call`：工具执行前，可阻断或改写参数。
- `permission_request`：需要审批时，可自动 allow/deny。
- `post_tool_call`：工具执行后，可记录、审计、生成额外上下文。

但 hooks 不能绕过 UI 可观测性。即使 hook 自动批准，也要在工具卡片/trace 中显示“由 hook 批准”。

## 15. Codex 主线总结：一次 shell 工具调用到底发生了什么

把上面的源码串起来，一次 shell 调用的真实路径是：

用户发消息后，模型输出 `shell_command`。

`ToolRouter` 把模型输出转成内部 `ToolCall`。这一步只做结构转换，不执行。

`ToolCallRuntime` 查看工具元数据。shell 声明支持并行，所以它可以拿读锁和其他可并行工具一起跑；shell 声明取消时等待 runtime 清理，所以用户停止时不会直接丢弃进程。

`ShellCommandHandler` 解析参数，得到 command、cwd、timeout、env、network、sandbox permissions。然后它调用 `ExecPolicy` 生成审批要求。

`ToolOrchestrator` 读取审批要求。需要审批就先跑 permission hooks，再走 guardian 或用户审批；不需要审批就记录决策。

审批通过后，`ToolOrchestrator` 选择第一次 sandbox attempt，并调用 `ShellRuntime.run()`。

`ShellRuntime` 根据当前 sandbox attempt 构造真正可执行的命令环境，合并 timeout 和 cancellation token，然后调用底层 exec。

`exec.rs` 启动进程，分片读取输出，限制输出大小，处理超时/取消，识别 sandbox denied。

如果第一次执行因为 sandbox 被拒绝失败，`ToolOrchestrator` 会判断是否允许二次审批和重试。允许时提示用户“是否脱离/提升沙箱重试”，用户批准后再执行第二次。

最后工具结果回到模型，同时前端收到工具 begin/progress/finish/error/cancel 事件。

这就是 Nova 应该对标的完整体感。

## 18. 结论：Nova 当前差距不是工具数量，而是运行时骨架

Codex 的强，不是因为它有一个神奇 bash 工具，而是因为它把一次工具调用从模型输出到真实系统副作用之间的每个环节都建模了。

Nova 现在如果继续加零散能力，会越做越难维护。正确路线是以 Codex 为主线，先把工具调用运行时重构出来：

- `ToolRouter` 统一接模型输出。
- `ToolCallRuntime` 统一并行和取消。
- `ExecPolicy` 统一权限决策。
- `ToolOrchestrator` 统一审批、沙箱、重试。
- `ProcessManager` 统一前台/后台进程。
- `Hooks` 统一外部策略。
- UI 只消费统一事件流。

做到这一步，Nova 才会从“封装了 Web UI 的聊天工具”变成“可以长期自用、可以开源展示、体感接近 Codex 的个人开发 Agent”。
